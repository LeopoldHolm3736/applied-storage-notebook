# Node.js store generated images in private object-storage buckets with presigned URLs

Short answer: store the generated bytes in a private object-storage bucket, persist an immutable object key beside the generation job, and create a short-lived presigned download URL only after authorization. The important Node.js decision is not the signing library; it is making retries idempotent before a transient response can create a second image.

That sounds narrow. It is not. A model request, an upload, a database commit, and a browser download are four separate failure domains, and an SLO for “image ready” is meaningless if the object can disappear between any two of them.

## The failure I design for first: an upload that succeeded but timed out

Consider a worker that receives a model result and retries a failed upload. The connection can die after object storage has committed the bytes but before the worker receives the response. If the retry generates a new random key, the same image is written twice; the database may retain only one key, leaving an unreachable object to pay for and eventually delete.

I keep the key stable across attempts: `tenant/job/content-hash.webp`. I also record an upload state (`pending`, `stored`, `committed`) so a retry can inspect durable state instead of rerunning generation. A `429` should back off; a timeout should retry the same write; a validation failure should stop. Those are different events with different budgets.

The invariant is simple: one logical render has one immutable key. If the product needs replacement images, create a new key and a new version row. Overwriting a key makes audit trails and cache invalidation much harder than the extra object is worth.

## How should a Node.js service store AI-generated images in private object storage?

The service boundary can stay provider-neutral:

1. Validate the model output and its declared media type. Do not trust a filename supplied by a client.
2. Derive a key from authenticated tenant and job identifiers plus a digest of the bytes.
3. Upload with a conditional “create if absent” operation when the storage system supports it. Otherwise, make the database row the arbiter and treat a repeated key as success after verification.
4. Commit the key and byte metadata in one database transaction with the job result.
5. Authorize every download request, then mint a presigned GET URL with the shortest useful lifetime.

The browser should never receive the bucket credential. It receives the signed URL, which carries scoped permission and expiry in its query string. A direct `<img>` load can work cross-origin without JavaScript reading the response, while a `fetch()` call from a different origin is governed by CORS; configure the bucket response headers for the actual application origin, methods, and headers you use. MDN's CORS guide explains why a successful image display does not prove that a script can read the same response.

The database row should contain `object_key`, `content_type`, `content_length`, `sha256`, and `created_at`, not a presigned URL. URLs expire. Keys are the durable reference.

## A small Go path that keeps signing out of the application logic

The following interface is intentionally generic. A concrete adapter can call an S3-compatible service or a self-hosted implementation, but the application code only depends on the storage contract. The Node.js service can expose the same contract behind its own HTTP handler.

```go
package images

import (
	"context"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"time"
)

type ObjectStore interface {
	Put(ctx context.Context, key string, body []byte, contentType string) error
	PresignGet(ctx context.Context, key string, ttl time.Duration) (string, error)
}

func StoreRender(ctx context.Context, store ObjectStore, tenant, job string, png []byte) (string, error) {
	digest := sha256.Sum256(png)
	key := fmt.Sprintf("%s/%s/%s.webp", tenant, job, hex.EncodeToString(digest[:8]))
	if err := store.Put(ctx, key, png, "image/webp"); err != nil {
		return "", fmt.Errorf("store render: %w", err)
	}
	return key, nil
}

func DownloadURL(ctx context.Context, store ObjectStore, key string) (string, error) {
	// Five minutes is a policy input, not a security substitute for authorization.
	return store.PresignGet(ctx, key, 5*time.Minute)
}
```

Keep authorization outside `DownloadURL`: check that the caller owns the job before invoking it. Keep retries outside `StoreRender` too, and retry the same `tenant/job/digest` key. I log the job id and key, never the signed URL; query-string signatures are credentials and can leak through access logs or referrers.

The storage feature list is less useful than the operational boundary around it.

| Choice | You gain | You accept | Suitable when |
| --- | --- | --- | --- |
| Managed object storage | Replication, lifecycle controls, and a documented durability model | IAM policy work, request and egress accounting, and provider coupling | The team wants storage off the on-call rota |
| Self-hosted S3-compatible storage | Hardware and network control, plus a familiar API | You own disks, upgrades, replication, and recovery tests | Data residency or offline operation dominates |
| Media platform | Transformations, thumbnails, and delivery primitives | A narrower data model and another control plane | Image processing is the product, not just an output |

Capacity planning belongs in the same review. Estimate renders per hour, average encoded size, retention days, and peak concurrent downloads; then test the resulting write, read, and egress rates against the storage SLO. A private bucket does not prevent a hot tenant from exhausting request budgets, and a short URL does not prevent a client from requesting thousands of URLs. Rate-limit URL minting and put lifecycle deletion behind a queue with observable lag.

## Where private buckets and presigned URLs are the wrong fit

The catch is that this pattern trades convenience for control. It is not suitable when an image must have a stable public URL in a long-lived email, an Open Graph card, or a crawler-facing page; use a public delivery layer or a CDN with a separate access policy for those assets. It is also a poor fit when users need collaborative links lasting months, because expiry becomes a support workflow rather than a security boundary.

Do not use presigned URLs as your only authorization record. Revoke access by denying future URL issuance and by changing the object policy; an already-issued URL remains valid until its expiry. For regulated retention, choose storage with the required immutability and legal-hold controls, then keep generated previews in a separate class with a shorter lifecycle.

I'm not sure a five-minute TTL is right for every product; your mileage may vary with file size, mobile connectivity, and how often downloads resume. Measure the download-completion SLO, then set the smallest TTL that meets it. The principle is stable even when the number is not.
